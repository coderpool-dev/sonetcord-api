# Контракты контроллеров и сервисов

DTO находятся в `app/Data` и объявлены как `final readonly`. Они описывают данные
операции, а Form Request продолжает отвечать за валидацию и авторизацию запроса.
Контроллер создаёт входной DTO из **проверенных** данных через `fromArray()`.
Сервис обращается к именованным типизированным свойствам, а не к ключам массива.

Основные контракты охватывают регистрацию, вход, восстановление пароля, сессии,
профиль, создание чатов, серверов, ролей, каналов и приглашений, загрузки,
обратную связь и жалобы, фильтры админки, клиентскую диагностику и сетевые замеры.
Вложенные настройки прав представлены `PermissionOverwriteData`.

Для частичных обновлений `Update*Data::fromArray()` сохраняет присутствие полей.
`has('topic')` отличает отсутствующее поле от явно переданного `null`, а `false`,
`0` и пустой список остаются переданными значениями. Конструкторы этих DTO закрыты,
чтобы нельзя было потерять информацию о присутствии поля при ручном создании.

`SessionContext` содержит IP, полученный через настроенный HTTP request, и
User-Agent. `AuthService`, `SessionService` и `DemoGuestService` не получают
HTTP Request; географию сессии определяет сервис по IP из этого контекста.

Результаты входа, демо-входа, обновления профиля, создания чата и звонка,
сохранения вложений типизированы. `toArray()` используется на границе JSON-ответа,
события, записи JSON в БД или внешнего транспорта.

Push передаётся между сервисами как `PushNotificationData`. `DeliverWebPush`
сохраняет массив в сериализованном задании и восстанавливает DTO перед отправкой:
это сохраняет совместимость с заданиями, поставленными в очередь прежней версией.

Списки ID, коллекции моделей, внутренние SQL-атрибуты и готовые представления
для HTTP остаются массивами или коллекциями. Диагностические поля отдельных
типов событий остаются валидируемыми словарями внутри типизированного события.

Сохранение контрактов проверяют существующие feature-тесты и
`tests/Feature/DtoContractsTest.php`.
